# 분류 기준과 합성 데이터 설계 (초안)

> 아래 건수·비율은 측정값이 아니라 **설계 값**이다.

## 1. 한 건의 VOC에 붙는 라벨 3개

한 건에 카테고리 1개, 심각도 1개, 감성 1개를 붙인다. 카테고리는 **가장 핵심인 것 하나**만 고른다(여러 주제가 섞여 있으면 경계 규칙 적용).

### 1-1. 카테고리 (6개)
| 코드 | 이름 | 이런 글 | 담당 조직(전파 대상) |
|---|---|---|---|
| BUG | 버그·오류 | 튕김, 접속 불가, 진행 불가, 표시 오류, 결제 오류, 데이터 손실 | 개발, QA |
| BAL | 밸런스 | 캐릭터·무기 강약, 난이도, 매칭 불균형 | 기획 |
| MON | 과금·확률 | 가격, 확률형 아이템 확률 의혹, 환불 요청, 패키지 구성 불만 | 사업, 기획, 고객센터 |
| OPS | 운영·공지 | 점검 시간, 공지 내용 오류·오해, 이벤트 보상 누락, 보상 기준 | 서비스 운영, 커뮤니케이션 |
| COM | 커뮤니티·불건전 이용 | 핵·매크로 의심, 비매너, 사기, 욕설, 제재 불만 | 서비스 운영, 제재 담당 |
| ETC | 기타 | 제안, 칭찬, 단순 문의, 위 어디에도 안 맞는 것 | 서비스 운영 |

### 1-2. 심각도 (4단계)
| 단계 | 기준 | 대응 |
|---|---|---|
| S1 긴급 | **글 한 건에는 부여하지 않는다(2026-11-17 변경).** 다수 유저에게 영향을 주는 접속 불가·결제 오류·재화 손실, 금전 또는 약속과 직결되는 공지 오기가 **같은 이슈 건수 누적 또는 데이터 확인으로 확인됐을 때 이슈 단위로** 부여 | 즉시 전파, 핫픽스·정정 공지 검토 |
| S2 높음 | 핵심 기능 오작동, 진행 불가, **접속 불가·결제 오류·재화 손실·공지 오기(글 한 건 기준)**, 확률·보상 관련 신뢰 훼손 의혹, 심각한 불건전 이용 | 당일 전파 |
| S3 보통 | 불편하지만 우회 가능한 오류, 밸런스·난이도 불만, 일반 제재 불만 | 주간 정리에 포함 |
| S4 낮음 | 제안, 칭찬, 단순 문의, 취향 | 월간 정리 또는 응답만 |

**심각도 경계 규칙 (2026-11-18, 4단계 오류 사례에서 도출, 사용자 확정)**
- 너무 어려워 진행이 막히거나 불공정하다는 불만은 S3. "너무 쉽다"나 구성이 아쉽다 같은 취향성 의견은 S4.
- 구매 전에 알 수 있던 패키지 구성·월정액 혜택이 아쉽다는 불만은 S4(이미 알고 결제한 것이므로, 사용자 판단). 표시나 공지와 다르다는 주장은 S2.
- 이벤트 보상을 못 받음, 진행 손실을 동반한 튕김, 퀘스트 완료 표시 안 됨은 S2(재화·약속·진행 손실). 업데이트 노트와 실제가 다르다는 "기대와 다름"은 S3.
- 이 규칙은 Set A·B의 오류 사례에서 뽑았으므로, 같은 글에서 규칙 적용 후 점수가 오르는 것은 낙관적인 값이다(02 4단계).

### 1-3. 감성 (3개)
긍정, 중립, 부정. 어조만 본다. **심각도와 독립**: 화난 어조의 사소한 불만은 부정 + S4일 수 있고, 차분한 접속 불가 제보는 중립 + S1일 수 있다. 이 차이를 AI가 구분하는지가 측정 포인트다.

### 1-4. 경계 규칙
1. 두 카테고리가 섞이면 **유저가 해결을 바라는 것**을 기준으로 한다("결제했는데 아이템이 안 들어와요"는 BUG, "확률이 너무 낮은 것 같아요"는 MON).
2. 공지 때문에 생긴 오해·항의는 OPS. 공지와 무관한 가격 불만은 MON.
3. 제재 불만은 COM. 제재가 오탐 버그라는 주장이면 BUG. 단 **유저의 주장만으로는 BUG로 옮기지 않는다**(정지는 재고 신청을 받는 불건전 이용팀 몫이고 버그로 인한 정지는 드묾). 같은 정지 불만이 여러 건 쌓이면 BUG로 재검토한다(2026-11-17, 사용자 판단).
3-1. 거래 중 아이템 미수령처럼 사기인지 시스템 오류인지 모를 때는 **빠른 처리를 위해 COM(제재 담당)으로 먼저** 보내고, 담당이 해당 유저에게 연락해 해결 여부를 확인하며, 사기면 법적 조치용 서류를 넘긴다(SYN-0067, 사용자 판단).
3-2. 매크로 의심 글은 글에 **자동화라고 볼 근거**(한 유저를 지목, 반복 패턴이 사람이 하기 어려움)가 있으면 COM. 같은 루트 반복이 보스 루트 같은 정상 플레이일 수도 있으면 BUG로 두고 모니터링 후 재분류한다(SYN-0026은 COM, SYN-0050은 BUG, 사용자 판단).
4. 판단이 갈리는 건은 정답셋에 `ambiguous=true`로 표시하고, 정확도는 전체와 ambiguous 제외 두 가지로 따로 잰다.

## 2. 규칙 보정 (AI 초안 위에 얹는 규칙, 후보)
AI가 낸 심각도를 아래 규칙이 **올리기만** 한다(내리지 않음). 규칙이 실제로 도움이 되는지도 측정 대상이다.
- 키워드 후보: 결제, 환불, 사라짐, 접속 불가, 소멸, 확률 조작 의혹 → 최소 S2.
- 같은 클러스터의 건수가 임계값을 넘으면 **S1로 올린다**(글 한 건의 심각도는 S2까지이므로 S1은 이 규칙으로만 생긴다, 2026-11-17 변경). 임계값은 6단계에서 정한다.

## 3. 합성 데이터 설계

### 3-1. 가상 서비스 설정
- **서비스는 l10n과 분리한다(2026-11-17 변경, 이전의 "공유" 결정을 대체).** l10n은 측정에 포켓몬(PokéAPI), 데모에 몬스터 헌터 용어를 쓴다. 둘 다 실제 IP라서, 그 용어를 VOC에 넣으면 실제 게임 유저의 의견처럼 보인다. 이 프로젝트의 규칙("실제 게임의 의견처럼 보이게 쓰지 않는다")과 충돌하므로 데이터는 섞지 않는다.
- VOC는 **독립된 가상 서비스**를 쓴다. 이름·장르·콘텐츠는 일반 명사로만 구성하고 실제 게임과 겹치지 않게 한다. 이름은 이 프로젝트에서 정한다(미정). 정해지기 전에는 본문에 서비스명을 직접 쓰지 않고 "이 게임" 같은 일반 표현이나 자리표시자 `{SERVICE}`를 쓴다.
- **연결은 시나리오의 문장 수준 인용으로만 유지한다(2026-11-17 확정, 2026-11-18 사용자 재확인: "문장 수준의 인용이면 괜찮다". 같은 날 먼저 "l10n과 별개로"라고 했다가, 연결이 데이터·서비스 공유가 아니라 문장 인용이라는 설명을 듣고 정정)**: 데이터·서비스·코드는 공유하지 않고 l10n 작업 진행과도 무관하다. 사고 대응 시나리오의 "재발 방지" 단계에서 l10n 검수기가 잡는 오류 유형(용어 불일치, 숫자·날짜 불일치, 언어 누락, 확률 합계)을 "이 유형이 새어 나갔다면 VOC에 이렇게 나타난다"로 인용한다. 시나리오 문구는 VOC 쪽 가상 서비스로 새로 쓴다.
- l10n 공지 5종 종류(점검, 업데이트 노트, 시즌 이벤트, 보상 지급, 확률 정보)와 VOC 카테고리의 대응(점검·시즌 이벤트·보상 지급은 OPS, 확률 정보는 MON)은 참고로만 쓴다.
- l10n 폴더는 읽기만 하고 수정하지 않는다.

### 3-2. 생성 방식
0. **합성 유지 원칙(2026-11-17 확정)**: 실제 게임의 VOC 원문은 수집·복사·게시하지 않는다. 실제 공개 리뷰는 "이런 종류의 불만이 있다"는 **유형을 주제 씨앗으로 참고하는 데만** 쓰고, 문장은 새로 쓴다. 특정 회사 게임을 연상시키는 이름·고유 콘텐츠는 쓰지 않는다.
1. 생성 지시표를 만든다: (카테고리, 심각도, 감성, 언어, 주제 씨앗) 조합.
2. LLM 한 개로 각 조합에 맞는 VOC를 생성한다(LM Studio 로컬, 두 모델 동시 로드 금지).
3. 생성 때 지정한 값이 **1차 라벨**(`label_status=generated`).
4. 사용자가 읽고 확정·수정한 것만 **정답**(`label_status=confirmed`). 정확도 측정에는 confirmed만 쓴다.
5. 일부러 **경계 사례**(두 카테고리가 섞임, 반어법, 영·한 혼합, 오타 많음)를 넣는다. 쉬운 건만 있으면 정확도가 의미 없다.

### 3-3. 규모 (설계 값)
- 총 100~200건. 첫 시도는 150건 안팎.
- 언어: 한국어 위주, 영어와 한·영 혼합을 섞는다.
- 시간축: 합성 타임스탬프로 7일치를 만들고, 그중 특정 이슈 하나가 특정 날에 급증하도록 설계한다(급증 감지 시험용).

### 3-4. 급증 시나리오 (사고 대응 한 장과 연결)
점검 시간 공지가 잘못 나가(예: 시각 표기 오류) 문의가 급증하는 상황을 하나 넣는다. 흐름: 오기 공지 → 관련 VOC 급증 → 급증 감지 → 담당 전달 → 정정 공지 → 재발 방지(l10n 검수 오류 유형을 한 문장으로 인용). 정확한 문구와 숫자는 데이터 생성 때 정한다.

### 3-5. 파일 스키마 (정답셋 CSV)
| 열 | 설명 |
|---|---|
| `id` | `SYN-0001`처럼 일련번호. 계정 ID처럼 보이는 값 금지 |
| `ts` | 합성 시각 |
| `lang` | ko / en / mixed |
| `text` | VOC 본문 (합성) |
| `gold_category` | BUG, BAL, MON, OPS, COM, ETC |
| `gold_severity` | S1 ~ S4 |
| `gold_sentiment` | pos, neu, neg |
| `gold_cluster` | 같은 이슈로 묶이는 그룹 이름(없으면 빈칸) |
| `ambiguous` | true / false |
| `label_status` | generated / confirmed |
| `is_synthetic` | 항상 true |
