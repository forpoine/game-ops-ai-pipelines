# VOC 파이프라인 결과 요약
> 전부 **합성 데이터**와 가상 서비스(`{SERVICE}`)다. 실제 게임·유저·사건이 아니다. 수치는 모두 이 프로젝트에서 잰 값이고, 근거와 경위는 `02_학습기록.md`에 있다. 이 문서는 확정된 기록을 옮겨 정리한 것이다(2026-11-18, Claude 작성, 용어집과 풀어쓴 설명 추가).

## 먼저 읽을 용어
이 분야를 처음 보는 사람도 읽을 수 있게, 본문에 나오는 말을 먼저 풀어 둔다.

### 일과 관련된 말
| 용어 | 쉬운 뜻 |
|---|---|
| 서비스 운영 | 게임이 출시된 뒤 문제 대응, 유저 소통, 공지, 이벤트, 운영 정책을 맡는 일 |
| VOC | Voice of Customer. 유저가 남긴 의견·문의·불만·제안. 게시판 글, 스토어 리뷰, 고객센터 문의 등. 이 문서에서는 글 한 건이 VOC 한 건 |
| 공지 오기 | 운영 측이 낸 안내문에 틀린 내용(시각, 보상 등)이 적힌 것 |
| 급증 | 같은 문제를 말하는 글이 짧은 시간에 갑자기 많이 들어오는 것. 무언가 터졌다는 신호 |
| 담당 조직 | 문제를 실제로 고칠 팀(개발, QA, 기획, 고객센터 등). 서비스 운영은 VOC를 정리해 이 팀들에 알린다 |
| 전파 | 정리한 내용을 담당 조직에 알리는 일 |
| 카테고리 | 글이 **무엇에 관한 것인가**. 버그, 밸런스(캐릭터 강약), 과금·확률, 운영·공지, 커뮤니티·불건전 이용, 기타의 6가지 |
| 심각도 (S1~S4) | **얼마나 급하게 봐야 하는가**. S1 긴급(즉시), S2 높음(당일), S3 보통(주간 정리), S4 낮음(월간 정리 또는 답변만) |
| 감성 | 글의 말투(긍정, 중립, 부정). 심각도와는 다르다. 화가 났어도 사소한 문제일 수 있고, 차분해도 심각한 문제일 수 있다 |

### AI와 측정에 관한 말
| 용어 | 쉬운 뜻 |
|---|---|
| LLM | 글을 읽고 쓰는 AI. 여기서는 인터넷에 보내지 않고 **내 PC에서 돌리는 모델**(로컬 LLM)을 썼다 |
| Gemma / gpt-oss / Qwen3 | 비교에 쓴 로컬 LLM 이름. 숫자(12B, 20B)는 모델 크기 |
| 합성 데이터 | 실제 유저 글이 아니라, AI에게 "이런 상황의 유저 글을 써 줘"라고 시켜 만든 가짜 글 |
| 정답셋 | 글마다 "이 글의 올바른 카테고리·심각도는 이것"이라고 미리 정해 둔 답안지. AI의 답을 이것과 맞춰 채점한다 |
| 정확도 | 맞힌 수 ÷ 전체 수 |
| %p (퍼센트포인트) | 퍼센트끼리의 차이. 60%에서 75%가 되면 15%p 올랐다고 한다 |
| 임베딩 | 글의 뜻을 숫자 목록으로 바꾼 것. 뜻이 비슷한 글은 숫자도 비슷해져서, 컴퓨터가 "이 두 글은 가깝다"를 계산할 수 있다 |
| 클러스터링(묶기) | 뜻이 가까운 글끼리 자동으로 한 묶음으로 모으는 일. 같은 문제를 말하는 글 100건을 이슈 1개로 보게 해 준다 |
| 코사인 거리 | 두 글의 임베딩이 얼마나 다른지 나타내는 값. 0에 가까울수록 뜻이 비슷하다 |
| ARI | 컴퓨터가 묶은 결과가 정답 묶음과 얼마나 같은지 나타내는 점수. **1이면 완전히 같고, 0이면 아무렇게나 묶은 것과 비슷하다** |
| 오탐 | 문제가 없는데 경보가 울린 것 |
| 일반화 | 어떤 글들을 보고 만든 방법이 **처음 보는 글**에서도 통하는지 |
| 같은 글에서 뽑은 규칙 | 결과를 보고 틀린 글에 맞춰 만든 규칙. 같은 글로 다시 재면 당연히 점수가 잘 나오므로, 새 글로 따로 재 봐야 진짜 효과를 알 수 있다 |

## 한 줄로
유저 글이 쏟아질 때 운영자가 하는 일(읽고, 나누고, 같은 이슈끼리 모으고, 터진 것을 알아채고, 담당 팀에 알리기)을 **AI가 초안을 만들고 규칙과 사람이 판단하는 구조**로 만들고, 단계마다 얼마나 맞는지 직접 쟀다.

## 무엇을 만들었나
글 한 건이 들어오면 아래 순서로 처리된다. 예를 들어 점검 공지에 종료 시각이 잘못 적혀서 "점검 끝났다면서 왜 접속이 안 되냐"는 글이 한국어·영어로 몰려드는 상황을 생각하면 된다.

1. **분류**: AI가 글마다 카테고리·심각도·말투를 붙인다. 위 예에서는 "운영·공지, S2, 부정"이 된다. 글 한 건만 보고는 최대 S2까지만 붙인다(한 사람의 글만으로 긴급이라고 단정하지 않기 위해).
2. **묶기**: 글을 임베딩으로 바꾸고 뜻이 가까운 글끼리 모은다. 한국어로 쓴 글과 영어로 쓴 글이 같은 문제라면 한 묶음이 되어야 한다.
3. **급증 감지**: AI가 아니라 **정해 둔 규칙**이 본다. 같은 묶음에 3시간 안에 5건 이상 들어오면 그 이슈 전체를 S1(긴급)로 올린다.
4. **전달**: 담당 팀에 보낼 요약을 만든다. 건수, 심각도, 담당 조직 같은 **숫자와 사실은 규칙이** 채우고, 내용 설명 세 문장만 AI가 쓴다. 한 묶음에 서로 다른 주제가 섞였으면 담당 팀을 하나로 찍지 않는다.
5. **최종 판단**: 사실 확인, 정정 공지 승인, 보상 결정은 사람이 한다.

| 단계 | 최종 구성 | 맡는 쪽 |
|---|---|---|
| 분류 | 로컬 LLM(Gemma 12B, gpt-oss 20B 비교). 글 한 건의 심각도는 S2까지 | AI |
| 묶기 | 다국어 임베딩(bge-m3) + 계층 클러스터링(코사인 거리 0.29를 기준으로 가까운 글끼리 묶음) | AI |
| 급증 감지 | 같은 묶음이 3시간 안에 5건 이상이면 이슈 단위 S1로 승격 | 규칙 |
| 전달 | 숫자·건수·담당 조직은 규칙, 본문 세 문장은 AI 초안 | 규칙 + AI |
| 최종 | 사실 확인, 정정 공지 승인, 보상 결정 | 사람 |

### 시험에 쓴 데이터
모두 AI로 만든 합성 글이다. 세 묶음으로 나눈 이유는 "한 묶음으로만 재면 점수를 믿기 어렵기" 때문이다.

| 이름 | 크기 | 왜 만들었나 |
|---|---|---|
| Set A | 150건 | 기본 시험지. Gemma가 썼고, 공지 오기로 몰린 급증 글 25건이 들어 있다 |
| Set B | 80건 | Gemma가 쓴 글을 Gemma가 채점하면 자기 말투라서 유리할 수 있다. 그래서 다른 모델(Qwen3)이 쓴 글로 한 번 더 쟀다 |
| Set C | 80건 | 4단계에서 결과를 보고 만든 규칙이 **처음 보는 글에서도 통하는지** 보려고 나중에 따로 만들었다 |

## 핵심 결과
| 무엇 | 결과 |
|---|---|
| 카테고리 분류 | 두 모델 91~98%. 다른 모델이 쓴 Set B에서도 Gemma가 앞섬(97.5%) |
| 심각도 분류(처음) | 58~61%. 큰 오류는 모델보다 기준과 정답 설계에서 나옴 |
| 심각도 기준 정비 후 | Set A 86~89%, Set B 87.5~90%. 단 같은 글에서 뽑은 규칙이라 낙관적 |
| 규칙의 일반화(Set C) | 한 모델 +15.0%p, 다른 모델 +6.3%p. 규칙을 비슷한 상황까지 넓혀 적용하는 부작용 발견 |
| 묶기(ARI) | 영어 중심 임베딩 0.24(A)·0.20(B) → 다국어 임베딩 **0.93(A)·0.84(B)** |
| 급증 감지 | 경보 1건, 오탐 0. 급증 첫 글 후 0.7시간(약 42분)에 울림 |
| 요약 초안 | AI가 쓴 본문 7개 중 2개를 사람이 고침 |
| 속도 | gpt-oss가 약 5배 빠름(건당 2.6초 대 13~14.6초) |

### 결과를 풀어 보면
- **"무엇에 관한 글인가"는 AI가 잘 맞혔다.** 카테고리는 두 모델 모두 열에 아홉 이상 맞혔다. 자기가 쓰지 않은 글(Set B)에서도 비슷했다.
- **"얼마나 급한가"는 처음에 절반 남짓만 맞았다.** 그런데 틀린 글을 하나씩 보니 AI가 이상하게 답한 게 아니라, 사람이 정한 기준과 정답 자체가 애매했다. 같은 주제의 글인데 정답이 어떤 건 S1, 어떤 건 S2로 들쭉날쭉했던 것이다. 그래서 기준을 고쳤다. 글 한 건으로는 S2까지만 주고, S1은 "같은 문제가 여러 건 쌓였을 때" 규칙으로만 준다. 애매했던 경계 세 군데에도 규칙을 정했다.
- **기준을 고치자 점수가 크게 올랐지만, 그대로 믿지 않았다.** 틀린 글을 보고 만든 규칙을 그 글로 다시 재면 당연히 잘 나온다. 그래서 새로 만든 Set C로 다시 쟀고, 한 모델은 15.0%p 올랐지만 다른 모델은 6.3%p에 그쳤다. 또 "퀘스트 완료 표시가 안 되면 S2"라는 규칙을, 게임 진행에는 지장 없는 업적 표시 오류(S3)에까지 넓혀 적용하는 부작용도 보였다. 이것은 규칙과 비슷하지만 해당하지 않는 함정 글(대조 글)을 일부러 섞어 넣어서 찾았다. 고친 프롬프트를 또 고치면 같은 글로 점수를 올리는 일이 반복되므로, 고치지 않고 한계로 남겼다.
- **묶기는 처음에 거의 실패했다가 모델 교체로 풀렸다.** 아래 "가장 중요했던 것"에 자세히 썼다.
- **급증 감지는 울려야 할 때 한 번 울렸고, 잘못 울린 적은 없었다.** 공지 오기 글이 처음 들어온 뒤 약 42분 만에 경보가 울렸다.
- **AI 요약은 그대로 보내지 않았다.** 7개 중 2개는 한두 건에만 나온 강한 표현(예: "게임을 그만두겠다")을 묶음 전체의 목소리처럼 썼다. 담당 팀이 알아야 할 신호라서 지우지는 않고, "일부 유저"의 의견으로 범위를 좁혔다.

## 과정에서 가장 중요했던 것: 고친 것을 다른 세트에서 다시 재기
결과를 보고 방법을 고치면, 그 결과에 맞춘 것이라 점수가 좋게 나오기 쉽다. 그래서 고친 방법은 반드시 **손대지 않은 다른 세트**에서 다시 재서, 거기서도 유지되는 것만 채택했다.

| 결과를 보고 고친 것 | 처음 세트 | 다른 세트 | 판단 |
|---|---|---|---|
| 언어별 평균 빼기(묶기 보정) | ARI 0.334 | 0.133 | 다른 세트에서 무너짐, 채택 안 함 |
| 다국어 임베딩으로 교체 | ARI 0.926 | 0.842 | 유지됨, 채택 |
| 심각도 경계 규칙 3개 | +8~18%p | +6~15%p(Set C) | 한 모델만 크게 유지, 한계로 기록 |

### 묶기 문제를 푼 과정
처음 쓴 임베딩 모델은 **뜻보다 언어로 글을 묶었다.** 같은 사고를 한국어로 쓴 글과 영어로 쓴 글이 다른 묶음으로 갈라졌고, 급증 글 25건이 13조각으로 쪼개졌다.

원인을 숫자로 확인했다. 글마다 가장 가까운 글을 찾아보니 150건 중 134건이 같은 언어의 글이었다. 서로 다른 주제의 글 사이 거리도, 같은 언어끼리는 0.069로 가깝고 다른 언어끼리는 0.201로 멀었다. 즉 "무슨 말을 하는가"보다 "어느 언어로 썼는가"가 거리를 좌우하고 있었다.

그래서 "영어 위주로 학습된 모델이라서 그렇다"는 가설을 세우고, **다른 조건은 그대로 두고 모델만** 여러 언어로 학습된 것으로 바꿔 다시 쟀다. 그러자 언어에 따른 거리 차이가 사라졌고(0.435 대 0.447), 급증 25건이 한 묶음이 됐다. 경보도 1.0시간에서 0.7시간으로 빨라졌다.

## 사고 대응 시나리오
공지에 점검 종료 시각이 잘못 적혀 VOC가 몰린 상황을 가정했다. 규칙이 급증을 잡아 S1로 올리고, 사람이 사실을 확인한 뒤 정정 공지를 승인한다. AI는 분류와 요약 초안까지만 맡는다. 사실 확인 없이 정정부터 냈을 때 무엇이 틀어지는지도 따로 적었다. 상세는 `03_사고대응시나리오.md`에 있다.

## 한계
- **합성 데이터다.** 실제 유저 글에는 오타, 밈, 여러 주제가 섞인 글이 훨씬 많으므로 실제 정확도는 말할 수 없다. 또 글을 만들 때 주제를 미리 정해 주었기 때문에 묶기 점수는 실제보다 높게 나왔을 것이다(추정).
- **모델을 바꾼 효과의 원인을 하나로 나눌 수 없다.** 다국어 임베딩이 잘된 것이 "여러 언어로 학습해서"인지 "모델이 더 커서"인지는 이 실험으로 구분할 수 없다.
- **급증 기준(3시간 5건)은 운영 판단으로 정한 값이다.** 이 설정으로는 급증이 대략 6~8건 이상이어야 안정적으로 잡힌다(정답 묶음 기준으로 잰 값). 자동으로 묶은 결과를 기준으로는 재지 않았다.
- **처리 시간은 비교하지 않았다.** 처음 목표였던 "사람이 직접 할 때 대 파이프라인" 처리 시간은 재지 않았다. 잰 것은 모델이 글 한 건을 분류하는 시간(2.6초, 13~14.6초)뿐이라, 운영자의 시간이 얼마나 줄어드는지는 말할 수 없다.
- **사람이 직접 확인한 정답은 일부다.** 애매한 경계 글(Set A 20건, Set B 11건)과 Set C 일부만 사람이 확정했고, 나머지는 글을 만들 때 지시한 값을 정답으로 썼다.

## 면접에서 한 문장 (단계별, 02에서 확정한 것)
- 분류 측정: 같은 글로 두 모델을 재 보니 카테고리는 91~98%인데 심각도는 58~61%였고, 큰 오류는 모델 능력보다 심각도 기준과 정답 설계에서 나왔습니다.
- 규칙 일반화: 같은 글에서 뽑은 규칙이 새 글에도 통하는지 따로 만든 세트로 재 보니 한 모델은 15%p 올랐지만 다른 모델은 6%p에 그쳤고, 규칙을 비슷한 상황까지 넓혀 적용하는 부작용도 대조 글로 찾아냈습니다.
- 묶기: 처음 쓴 영어 중심 임베딩은 주제보다 언어로 묶여 같은 사고를 한국어·영어로 쓴 글이 갈라졌는데(ARI 0.24), 다국어 임베딩으로 바꾸자 같은 절차에서 0.93, 따로 만든 세트에서도 0.84가 나와 문제는 데이터보다 모델 선택에 있었다고 봅니다.
- 급증 감지: 급증 감지는 처음엔 25건이 13조각으로 쪼개진 상태에서 조각 하나 덕분에 울린 취약한 성공이었는데, 임베딩을 바꿔 한 덩어리로 묶이자 정답 주제 기준과 같은 시각에 울려서, 감지 성능은 클러스터링 품질에 묶여 있다고 봅니다.
- 사고 대응: 공지 오기로 VOC가 몰리면 규칙이 급증을 이슈 단위 S1로 올리고, 정정 공지는 사람이 사실을 확인한 뒤에만 냅니다. AI는 분류와 초안까지만 맡습니다.
- 회고: 결과를 보고 고친 것이 여러 번 있었는데, 그때마다 손대지 않은 다른 세트에서 다시 재서 유지되는 것만 채택했고, 다시 한다면 그 검증 세트를 처음부터 떼어 두겠습니다.

## 예상 질문
### 사람이 검수하지 않은 글은 AI가 제대로 처리했다고 어떻게 확신하나요?
> 단정할 수는 없습니다. 이 프로젝트에서 사람이 직접 확정한 정답은 애매한 경계 사례뿐이고, 나머지는 데이터를 만들 때 지시한 값이라 그 자체도 틀릴 수 있습니다. 실제로 지시값이 틀리고 모델이 맞은 사례도 나왔습니다. 그래서 한계로 기록했습니다. 실제 운영이라면 전수 검수 대신 무작위 표본 검수로 오류율을 재고, 두 모델의 답이 다르거나 형식이 깨진 글만 사람에게 보내서 볼 범위를 좁히겠습니다.

- 더 물으면: 글 한 건은 S2까지만 받고 긴급(S1)은 같은 문제가 쌓였을 때 규칙으로만 올리므로, 한두 건을 잘못 분류해도 큰 사고는 건수로 잡힌다. 담당 조직과 숫자도 규칙이 채워서 AI 오류가 퍼지는 범위가 좁다. 다만 이것은 오류가 덜 퍼지게 할 뿐 오류가 없다는 증거는 아니다.
- 피할 말: "사람이 최종 검수하니 괜찮다"(사람이 모든 글을 보지 않는다), "정확도가 90%를 넘으니 믿을 만하다"(그 점수를 낸 정답도 일부만 검증됐다).

### 사람을 대체하는 AI 분류 프로젝트인가요?
> 아닙니다. 운영 업무에 AI를 넣을 때 어디까지 맡기고 어디부터 사람과 규칙이 잡을지를 나누고, 그 결정을 숫자로 확인한 프로젝트입니다. 글 한 건만 보고는 긴급을 주지 않게 막았고, 요약의 숫자와 담당 조직은 규칙이 채우며, AI 요약 7개 중 2개는 사람이 고쳤고, 정정 공지와 보상은 사람이 결정합니다.

### 회사가 이미 비슷한 도구를 쓰고 있다면 이 프로젝트는 무슨 의미가 있나요?
> 이미 도구가 있다면, 저는 그 도구가 우리 기준에서 얼마나 맞는지 재고, 틀리는 곳을 찾아 기준이나 사람 검수로 메우는 역할을 할 수 있습니다. 이 프로젝트는 도구를 만든 경험보다 도구를 평가하고 의심한 경험입니다.

- 틀리는 원인을 짚는다: 심각도가 58~61%였을 때 틀린 글을 하나씩 보니 원인은 모델보다 기준 문구의 모호함이었다. 기준을 정하는 것은 운영 정책의 일이다.
- 좋아 보이는 점수를 믿지 않는다: 결과를 보고 고친 방법은 손대지 않은 세트에서 다시 재서 유지되는 것만 채택했다. 언어별 평균 빼기는 처음 세트에서 좋아 보였지만 다른 세트에서 무너져 버렸다.
- 어디서 깨지는지 안다: 한국어·영어가 섞이면 같은 사고가 갈라질 수 있음을 직접 봤다. 글로벌 서비스에서 부딪힐 수 있는 문제다.
- 고칠 수 있는 말로 전달한다: "AI가 이상하다"가 아니라 "이 기준 문구가 애매해서 S2와 S3가 갈린다"처럼 개발·기획이 바로 움직일 수 있게 말한다.
- 과장하지 않을 것: 합성 데이터 수백 건의 작은 실험이라 실제 서비스 규모에서 돌아간다는 증거는 아니다. 코드는 AI가 썼고, 내세울 것은 설계·판단·검증이다.
